# 개발 기준

## 검증 기준

배포 전에는 `pnpm typecheck`, `pnpm test`, `pnpm lint`, `pnpm build`를 통과해야 한다. 페이지 경계, 서버 액션, 미들웨어, 마이그레이션을 바꾼 작업은 빌드까지 확인하지 않으면 완료로 보지 않는다.

엑셀 파서, 재고 계산, 사용자 그룹, 권한, 에러 매핑, RPC 입력 모양을 바꾸면 단위 테스트를 추가하거나 기존 테스트를 갱신해야 한다. 업무 규칙이 바뀌었는데 테스트가 그대로 통과하면 누락이다.

인증 경로, 관리자 경로, 그룹 제한 경로를 바꾸면 Playwright 인증 스모크 또는 해당 로컬 시나리오를 확인해야 한다. 라우트만 바꾸고 미들웨어·메뉴·서버 액션을 함께 바꾸지 않으면 권한 불일치가 생긴다.

## 서버 액션

서버 액션은 입력 검증을 먼저 수행하고, 그 다음 권한 가드를 통과한 뒤 데이터 변경을 호출한다. 검증 전 DB 변경, 권한 확인 전 파일 업로드, 실패 후 남은 임시 파일은 허용하지 않는다.

관리자 전용 작업은 `requireAdmin`을 사용한다. 모든 활성 사용자에게 열린 작업은 `requireSignedIn`을 사용한다. 2그룹을 막아야 하는 구매·예치금·엑시트몰 흐름은 `requireUserGroup1`을 사용한다.

RLS와 RPC가 권한을 직접 검증해 앱에서 사용자 ID가 필요 없는 액션은 가드 없이 `createClient()`를 쓸 수 있다. 이 경우 코드에 RLS가 권한을 검증한다는 짧은 주석이 있어야 하며, 작성자 비교가 필요한 액션에는 적용하면 안 된다.

서버 액션 반환은 성공과 실패가 명확한 `ActionResult` 계열을 유지한다. 사용자가 보는 오류에는 SQL 함수명, RLS 정책명, service role 여부 같은 내부 정보를 노출하지 않는다.

변경 후에는 관련 고객 화면과 관리자 화면을 함께 `revalidatePath` 처리한다. 고객에게 보이는 상태만 갱신하고 관리자 검토 목록이 낡은 상태로 남으면 운영 실수가 생긴다.

## 데이터 변경

예치금, 재고, 승인 상태처럼 여러 데이터가 함께 움직이는 변경은 RPC로 처리한다. 앱 코드에서 여러 테이블을 순차 업데이트해 원자성을 흉내 내면 안 된다.

마이그레이션은 누적 방식으로 작성한다. 이미 배포된 마이그레이션 파일을 고쳐 과거 상태를 바꾸지 않는다. 상태 값 추가, CHECK 변경, RLS 변경은 새 파일로 남긴다.

`lib/db-types.ts`는 DB 스키마를 바꾼 뒤 로컬 Supabase 기준으로 다시 생성해야 한다. 타입 파일만 수동 수정하면 다음 타입 생성 때 사라지고 실제 DB와 맞지 않는다.

직접 테이블 삽입 정책을 열 때는 같은 흐름의 RPC 검증을 우회하지 않는지 확인한다. `stock_orders`와 `order_uploads`는 고객이 임의 JSON을 넣어 승인 로직을 속일 수 없는 구조여야 한다.

## 파일과 엑셀

업로드 파일명은 안전한 이름으로 정규화하고, 사용자 ID나 요청 ID를 포함한 경로 아래 저장한다. 원본 파일명이 그대로 Storage 경로가 되면 충돌, 경로 조작, 운영자 다운로드 혼선이 생길 수 있다.

배송대행 양식과 입고리스트 양식은 헤더로 구분한다. 한 흐름에 다른 양식이 올라오면 저장 전에 거부해야 한다. 헤더 허용 범위를 넓힐 때는 잘못된 양식을 통과시키지 않는 테스트를 같이 바꾼다.

송장 재업로드는 송장번호만 갱신한다. 송장 파일의 상품명, 수량, 받는사람 값으로 기존 업로드 본문을 덮어쓰면 안 된다.

## UI 기준

운영 화면은 정보 밀도와 반복 처리 속도를 우선한다. 테이블, 상태 배지, 필터, 명확한 검토 버튼을 사용하고 장식용 대형 히어로, 과한 애니메이션, 카드 중첩을 넣지 않는다.

금액은 원화 표기와 우측 정렬을 유지한다. 상태는 성공, 경고, 위험, 정보 계열의 제한된 색상으로 표현하고 색상만으로 의미를 전달하지 않는다.

Server Component를 기본으로 쓰고, 폼 상태, Realtime, 파일 업로드, 토스트처럼 상호작용이 필요한 곳만 Client Component로 분리한다. 페이지 전체를 불필요하게 클라이언트 컴포넌트로 바꾸면 세션 조회와 권한 검사가 흐려진다.

shadcn/ui 컴포넌트는 기존 variant와 `cn()` 조합 방식을 유지한다. 공용 컴포넌트를 수정하면 관리자와 고객 화면 양쪽의 밀도, 터치 영역, 접근성을 확인한다.

목록 테이블은 좁아질 때 열을 줄이지 말고 가로로 스크롤시킨다. `w-full` 테이블은 폭이 모자라면 열을 압축하는데, 한글은 이때 한 글자씩 세로로 접혀서 "접/수", "이/민/진"처럼 읽을 수 없게 된다. 테이블에 `whitespace-nowrap`을 걸고 컨테이너를 `overflow-x-auto`로 감싼다. 길게 늘어나도 되는 설명 열(제목, 상품명, 배송지)만 남는 폭을 흡수하게 하고, 필요하면 `truncate`로 줄인다.

열을 추가할 때는 추가한 열만 보지 말고 같은 테이블의 좁은 열(상태, 날짜, 금액, 수량, 작성자)이 함께 접히지 않는지 확인한다. 시드 데이터는 이름이 짧아 문제가 드러나지 않으므로, 운영에 가까운 긴 값으로 확인한다.

## 코드 구조

라우트 파일은 화면 조립과 해당 화면에 필요한 조회 호출을 맡는다. 업무 규칙, 파서, 권한 판단, 상태 전이 검사는 `lib/`로 내려 중복 구현을 피한다.

공유 타입과 상태 라벨은 한 곳에서 관리한다. 같은 상태 문자열을 화면마다 새로 정의하면 CHECK 제약, RPC, 배지가 어긋난다.

Supabase 타입 우회가 필요하면 공용 헬퍼 경계에 모은다. 호출 지점마다 `as any`를 퍼뜨리면 리뷰가 어려워지고 실제 스키마 불일치가 묻힌다.

절대 import 별칭 `@/`를 사용한다. 깊은 상대 경로가 늘어나면 라우트 그룹 이동 때 깨지기 쉽다.

## Git

문서, 앱 코드, 마이그레이션은 관련 변경 단위로 묶는다. DB 계약을 바꾸는 코드만 커밋하고 마이그레이션을 빠뜨리면 로컬 테스트와 배포가 서로 다른 앱이 된다.

생성 산출물, 로컬 비밀, 테스트 리포트, 빌드 결과는 커밋하지 않는다. 로컬 작업 기록, `.next/`, `.env*`, Playwright 결과물, 로컬 엑셀 산출물은 작업 상태에 남아도 버전 관리 대상이 아니다.
