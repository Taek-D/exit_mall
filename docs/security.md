# 보안 정책

## 보호 대상

고객별 예치금, 주문, 보유 재고, 배송대행 업로드, 입고 요청, CS 문의, 첨부 파일은 고객 간에 섞이면 안 되는 데이터다. 한 고객의 엑셀 원본, 송장 파일, 입고 첨부, 문의 첨부가 다른 고객에게 보이면 개인정보와 거래 정보가 함께 노출된다.

상품 이미지는 공개 버킷에 둘 수 있지만, 상품 관리 권한은 관리자에게만 있다. 주문·입고·문의 파일은 비공개 버킷에 두고, 앱이 권한을 확인한 뒤 필요한 링크를 발급한다.

service role 키는 서버 전용 비밀이다. 브라우저로 전달되면 모든 RLS 우회 권한이 노출되므로 환경 변수 이름이 `NEXT_PUBLIC_`으로 시작하면 안 된다.

## 인증 흐름

공개 경로는 로그인, 가입, 승인대기 안내, 아이디 찾기, 비밀번호 재설정, 인증 콜백, 공개 가입 API, 배송조회 API로 제한한다. 그 외 경로는 미들웨어에서 Supabase 세션을 확인한다.

세션이 없으면 로그인 화면으로 보낸다. 세션은 있지만 프로필이 없으면 로그인 화면으로 되돌린다. 프로필 상태가 `active`가 아니면 승인대기 화면으로 보내고, 현재 상태를 안내한다.

관리자 경로는 `role='admin'`이 아니면 고객 상점 화면으로 보낸다. 2그룹 고객이 허용되지 않은 고객 경로로 들어오면 사입재고 배송대행 홈으로 보낸다. 루트 경로는 관리자면 관리자 홈, 2그룹이면 사입재고 배송대행, 그 외 고객이면 상점으로 보낸다.

비밀번호 재설정은 Supabase Auth 콜백 방식과 이름·전화번호·이메일을 확인하는 직접 재설정 흐름이 함께 있다. 직접 재설정은 시도와 확인 데이터를 별도 테이블에 남기며, 공개적으로 사용자를 특정할 수 있는 과한 오류 정보를 반환하면 안 된다.

## 권한 모델

비로그인 사용자는 공개 인증 화면과 공개 가입 API만 사용할 수 있다. 비로그인 사용자가 고객 데이터, 관리자 데이터, 비공개 파일 링크를 얻으면 안 된다.

승인대기, 정지, 거절 사용자는 공개 안내 화면 외 업무 기능을 사용할 수 없다. 세션이 있어도 주문, 입고, 문의, 첨부 링크 발급을 허용하면 안 된다.

1그룹 활성 고객은 상점, 상품 구매, 예치금 요청, 엑시트몰 배송대행, 사입재고 배송대행, 입고리스트, CS 문의, 계정 기능을 사용할 수 있다. 다른 고객의 행이나 파일은 조회·수정·다운로드할 수 없다.

2그룹 활성 고객은 사입재고 배송대행, 입고리스트, CS 문의, 가이드, 계정 기능만 사용할 수 있다. 상점, 상품 구매, 예치금, 엑시트몰 배송대행, 일반 보유 재고 기능을 메뉴와 서버 액션 양쪽에서 막아야 한다.

관리자는 전체 운영 데이터를 조회하고 상태를 바꿀 수 있다. 현재 정책상 관리자를 고객별로 나누는 제한은 없다. 관리자도 고객 본인으로 위장한 직접 삽입을 통해 검증을 건너뛰면 안 되고, 핵심 처리는 관리자 전용 서버 액션과 RPC를 통해 수행해야 한다.

RLS만으로 충분한 액션은 RPC가 작성자, 관리자 여부, 활성 상태를 직접 검증하는 경우다. 사용자 ID를 앱 코드에서 비교해야 하는 댓글 수정·삭제 같은 액션은 서버 액션 가드를 먼저 통과해야 한다.

## 파일 접근

상품 이미지는 공개 읽기를 허용하되 쓰기, 수정, 삭제는 관리자만 가능하다. 상품 이미지 외 파일은 원칙적으로 비공개다.

배송대행 원본과 송장 파일은 업로드 소유자와 관리자만 읽을 수 있다. 고객이 다른 고객의 파일 경로를 알아도 다운로드 링크를 얻으면 안 된다.

입고리스트와 CS 문의 첨부는 요청 소유자와 관리자만 읽을 수 있다. 첨부 경로는 요청 ID와 사용자 소유권을 검증할 수 있는 구조여야 하며, 임의 경로 삽입으로 다른 요청에 파일을 붙일 수 없어야 한다.

CS 댓글 이미지는 관리자 댓글에만 붙일 수 있다. 일반 고객 댓글에 이미지를 붙이는 기능이 필요해져도, 현재 정책을 바꾸기 전까지는 서버 액션과 DB 정책 양쪽에서 거부해야 한다.

## 감사와 추적

예치금 증감은 `balance_transactions`에 금액, 처리 후 잔액, 참조 종류, 참조 ID, 관리자 ID 또는 메모가 남아야 한다. 잔액만 바뀌고 거래 기록이 없으면 운영자가 고객 문의를 검증할 수 없다.

보유 재고 증감은 엑시트몰 상품 재고와 사용자 수기 재고 각각의 변동 기록에 남아야 한다. 승인, 배송대행 차감, 관리자 수동 조정은 출처가 구분되어야 한다.

사입재고 관리자 수동 등록과 수정은 조정 기록에 남아야 한다. 입고 요청에서 생성된 로트와 관리자 수동 로트는 출처가 구분되어야 한다.

관리자 승인, 반려, 상태 변경, 송장 등록 실패는 서버 로그에 원인과 대상 ID를 남긴다. 사용자에게는 내부 오류 코드나 SQL 세부 정보 대신 업무 문맥의 메시지를 보여준다.

## 보안 헤더와 설정

모든 경로에는 프레임 삽입 방지, MIME 스니핑 방지, 엄격한 referrer 정책, HSTS, 카메라·마이크·위치 권한 차단 헤더가 붙는다. 새 배포 대상이 HTTPS가 아니면 HSTS가 개발 테스트를 방해할 수 있으므로 로컬과 프로덕션 설정 차이를 확인해야 한다.

환경 변수는 Supabase URL, anon key, service role key, 사이트 URL로 나뉜다. anon key는 브라우저 공개가 가능하지만 service role key는 서버에서만 읽어야 한다. 사이트 URL은 비밀번호 재설정과 외부 콜백의 기준 주소다.
