# lib 영역 기준

## 책임

`lib/`는 업무 규칙에 가까운 코드와 서버 액션, Supabase 클라이언트, 파서, 권한 판단, 조회 헬퍼, 에러 매핑을 가진다. 화면이 달라도 같은 업무 규칙은 여기에서 한 번만 정의한다.

`lib/actions/`는 데이터 변경의 앱 쪽 입구다. 입력을 검증하고 권한을 확인한 뒤 RPC나 제한된 테이블 쓰기를 호출한다.

`lib/supabase/`는 실행 위치별 클라이언트를 제공한다. 서버, 브라우저, 미들웨어 클라이언트가 섞이면 쿠키 처리와 권한 경계가 깨진다.

## 경계

예치금, 보유 재고, 사입재고, 승인 상태를 앱 코드에서 직접 맞물려 갱신하지 않는다. 원자성이 필요한 변경은 RPC로 맡긴다.

파서와 매칭 유틸은 UI 문구나 컴포넌트 상태를 알면 안 된다. 입력 파일을 업무 데이터로 바꾸고, 실패 이유를 호출자가 표시할 수 있는 오류로 돌려주는 데 집중한다.

service role 클라이언트는 제한된 서버 작업에서만 만든다. 일반 조회나 고객 액션에 service role을 쓰면 RLS가 검증해야 할 소유권이 사라진다.

## 구현 방식

서버 액션은 검증, 권한, 변경, 캐시 갱신 순서를 유지한다. 실패 시 이미 올린 파일이 있으면 정리하고, 사용자에게는 업무 문맥의 오류를 반환한다.

사용자 그룹 제한은 `requireUserGroup1`을 사용한다. `user_group`이 비어 있는 사용자는 1그룹으로 취급하는 정책을 유지한다.

배송대행 상품 매칭은 현재 이름 기반이다. 임의로 첫 번째 후보를 고르지 말고, 중복되면 운영자가 정리할 수 있는 오류를 반환한다.

엑셀 파서는 헤더 검사와 필수값 검사를 먼저 한다. 배송대행 양식과 입고리스트 양식이 서로 잘못 올라오면 저장 전 거부한다.

## 테스트 기준

파서, 매칭, 가용 재고 계산, 가용 예치금 계산, 권한 판단, 에러 매핑을 바꾸면 단위 테스트가 필요하다.

서버 액션에서 RPC 입력 모양을 바꾸면 RPC 테스트나 액션 테스트로 실제 전달 형태를 확인한다.
