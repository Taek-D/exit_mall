# app 영역 기준

## 책임

`app/`은 라우트, 레이아웃, 서버 컴포넌트, 페이지별 화면 조립을 맡는다. 이 영역은 고객과 관리자가 어떤 흐름을 보는지 결정하지만, 예치금 차감, 재고 증감, 승인 상태 전이의 최종 규칙을 직접 구현하지 않는다.

고객 라우트는 `(user)` 아래에 모이고, 관리자 라우트는 `(admin)/admin` 아래에 모인다. 공개 인증 라우트는 `(auth)`와 `auth/callback`에 있다. 새 화면을 추가할 때는 누가 접근하는 화면인지 먼저 정하고 같은 그룹의 레이아웃과 네비게이션 규칙을 따른다.

## 경계

페이지 파일에서 Supabase 테이블을 직접 여러 개 갱신하지 않는다. 변경 작업은 서버 액션이나 RPC로 보낸다.

관리자 화면을 고객 화면의 조건부 분기로 섞지 않는다. 관리자와 고객은 같은 데이터를 보더라도 권한, 표시 밀도, 가능한 액션이 다르다.

2그룹에서 막아야 하는 화면은 메뉴에서 숨기는 것만으로 끝내지 않는다. 미들웨어와 서버 액션 가드가 같은 정책을 가져야 한다.

## 구현 방식

서버 컴포넌트를 기본으로 사용한다. 폼 제출 상태, 업로드, 토스트, Realtime 구독, 모달 열림 상태처럼 브라우저 상호작용이 필요한 부분만 클라이언트 컴포넌트로 분리한다.

페이지에서 필요한 데이터 조회는 가능한 한 `lib/admin`, `lib/orders`, `lib/support`, `lib/inbound` 같은 조회 헬퍼로 내려 중복을 줄인다. 같은 count, status label, 날짜 포맷을 페이지마다 새로 만들지 않는다.

리다이렉트 호환 경로는 기존 사용자 책갈피를 깨지 않기 위해 유지한다. `/orders/upload`, `/shipping-uploads`, 관리자 구 배송대행 경로처럼 의미가 바뀐 경로는 명확한 새 목적지로 보낸다.

## 테스트 기준

인증, 관리자 접근, 그룹 제한, 주요 리다이렉트를 바꾸면 E2E 또는 로컬 시나리오 테스트를 확인한다.

페이지가 서버 액션 결과를 표시하는 방식을 바꾸면 성공, 업무 오류, 권한 오류, 검증 오류가 화면에 다르게 보이는지 확인한다.
